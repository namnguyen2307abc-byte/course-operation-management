I. Overview
1. System Context 
The Multi-Discipline Training Center Academic Operations Management System is designed to support and digitalize the academic operations of a multi-discipline training center. The system supports key processes such as course and class management, trial and placement, enrollment, scheduling, attendance, make-up lessons, student assessment and progress tracking, and tuition payment.
The system interacts with Parents, Students, Academic Staff, Branch Managers, Teachers, Admin, and an external Payment Gateway. Each entity exchanges information with the system according to its responsibilities and access permissions. 


  





2. External Entities


#
	Entity
	Description
	1
	Parent
	Searches available courses and classes, submits and tracks enrollment requests for their children, requests a placement test when needed, and cancels eligible requests. Parents can also submit absence requests and view related learning information. 
	2
	Academic Staff 
	Creates and updates classes based on existing courses and branches. Reviews enrollment requests, checks placement recommendations when applicable, and assigns students to suitable open classes. Staff may also arrange placement tests and make-up lessons in the relevant modules. 
	3
	Teacher 
	Evaluates placement tests, records assessment results and course recommendations, reviews absence requests, and records student attendance. 
	4
	Admin 
	Performs authorized administrative tasks across the system, including managing classes, reviewing enrollment requests, and views branch facilities and updates permitted room and equipment information and conditions. Reviews room usage and facility warnings. 
	5
	Payment Gateway 
	PayOS provides payment links or QR codes and sends transaction results to the system through a webhook. The system uses these results to process the related tuition payment.

5.3 Non-UI Functions
#
	Feature
	System Function
	Description
	1
	Authentication
	Authentication and JWT validation
	POST /api/auth/login verifies an ACTIVE user with BCrypt. JwtService signs a token; JwtAuthenticationFilter validates its signature, expiry and version against the current account on subsequent requests.
	2
	Authentication
	Public parent registration
	POST /api/auth/register validates username, password and duplicate username/email, rejects a non-PARENT role, hashes the password and issues an authentication response.
	3
	Authentication
	Password and session lifecycle
	POST /api/auth/change-password locks the account, verifies the old password, increments tokenVersion and clears mustChangePassword. Requests carrying an old token are rejected.
	

#
	Feature
	System Function
	Description
	4
	Course Enrollment
	Enrollment validation and seat calculation
	CourseEnrollmentService verifies child ownership, prevents an additional open request, excludes unavailable classes and subtracts both enrolled students and pending-payment reservations from available seats.
	5
	Course Enrollment
	Enrollment cancellation
	PATCH /api/course-enrollment/requests/{id}/cancel locks the owned request and checks its status, class/enrollment assignment and any linked placement schedule before marking CANCELLED.
	6
	Placement Test / Course Enrollment
	Placement linkage and recommendation
	Assessment saves the recommended course and result on the schedule. A linked WAITING_PLACEMENT enrollment request becomes READY_FOR_ASSIGNMENT. Recommendation lookup prefers the latest linked schedule and falls back to legacy PlacementTest data only when no linked schedule exists.
	7
	Course Enrollment
	Enrollment decision and invoice creation
	Staff decision validates request state, OPEN class, compatible course, capacity and duplicate enrollment. Approval creates PENDING_PAYMENT enrollment and an UNPAID invoice with a due date one month later; it does not immediately increase official class occupancy.
	8
	Class Management
	Scheduled lesson generation
	ClassSchedulingService generates lessons from selected weekdays and times. The session count uses the submitted value, otherwise the course session count, otherwise 12, and must be between 1 and 60. It validates the calculated end date, class readiness, teacher and room suitability, schedule conflicts, and the teacher’s minimum 30-minute break. Generation is request-triggered. 
	9
	Weekly Schedule
	Weekly schedule and roster assembly
	GET /api/schedule/weekly filters by role and linked student/teacher. ScheduleWeeklyServiceImpl adjusts original and target lessons for make-up cases and assembles the attendance roster with regular and make-up students.
	#
	Feature
	System Function
	Description
	10
	Attendance
	Attendance persistence and make-up completion
	POST /api/schedule/lessons/{id}/attendance validates the actor, lesson and submitted roster before saving a batch. PRESENT attendance completes a matching scheduled make-up. The GET attendance-sheet response supplies canEdit and the reason when editing is locked.
	11
	Absence and Make-up
	Absence review and make-up creation
	Review accepts APPROVED, EXCUSED or REJECTED for a PENDING request. EXCUSED and REJECTED require a note. Only APPROVED creates a pending make-up registration.
	12
	Absence and Make-up
	Make-up candidate selection and resolution
	The service searches other classes for a compatible session using program/level, or the same course fallback when level data is missing. It removes unusable or full candidates. Personnel can schedule, cancel, mark NO_SLOT or DEFERRED; deferral does not itself enroll a student in a future course.
	13
	Branch Facility
	Facility validation
	Room updates validate capacity against the maximum enrollment of classes using the room and allow type changes only when the new type remains compatible. MAINTENANCE is blocked while ongoing or upcoming SCHEDULED lessons use the room. Equipment updates save the recorded condition and return applicable shortages and affected-lesson warnings without automatically changing schedules. 
	14
	Tuition Payment
	Discount calculation and approval
	PaymentCollectionService recalculates finalAmount from the invoice original amount and approved discount. Amounts are non-negative whole VND within the configured validation bound; changing the discount requires ADMIN and a reason.
	15
	Tuition Payment
	Cash and manual bank collection
	POST /api/tuition-payment/process delegates to PaymentCollectionService. Cash validates tender/change and confirms immediately. Manual bank submission requires a unique reference and owned proof, remains PENDING, and waits for another ADMIN to approve or reject.
	

#
	Feature
	System Function
	Description
	16
	Tuition Payment
	PayOS link and verified webhook
	PayOSGateway uses RestClient and HMAC-SHA256. A created online request stores orderCode and expectedAmount. The public webhook checks signature, successful status, order, exact amount and transaction reference. A duplicate of the same confirmed transaction returns its existing receipt.
	17
	Tuition Payment
	Payment finalization
	A successful confirmation runs finish(): locks related records, marks the invoice PAID, changes the enrollment to ENROLLED, increments occupancy only on the first enrollment transition, and approves its linked pending-payment enrollment request.
	18
	Tuition Payment
	QR generation and status polling
	The VietQR service constructs a QR image URL and transfer information; it does not receive money. The browser periodically calls invoice status while a payment dialog is active. Polling and payment return pages do not substitute for successful server confirmation.
	19
	Financial Reporting
	Cash handover and financial reporting
	Expected cash is calculated from successful collections. Submission records expected and declared amounts; a second administrator records actual received cash or returns the statement. Submitted/confirmed days block additional cash collection until returned. Reports and audit are queried on demand.
	20
	File Storage
	Attachment and proof storage
	Shared FileStorageService writes placement attachments under uploads. FinanceProofService stores PNG/JPEG/PDF proof files up to 5 MB, verifies file signatures and ownership and serves authorized files through the protected proof API.
	21
	System Administration
	Administrative Audit Service
	Account management records administrative changes with the responsible actor. Administrative audit queries return searchable, paginated records to the Admin Audit screen. Financial operations use a separate finance audit service.
	

No scheduled batch or cron task is configured in the reviewed Java application. Lesson generation is triggered by a request; payment status polling is triggered by the browser. An invoice due date does not automatically implement 24-hour cancellation, a nightly reconciliation or a refund process.

1.2 Class Maintenance 
1.2.1 Create Class 
  

  

  











This form allows Staff, Admin, and Branch Manager users to create a class based on an existing course and an active branch. Users enter class information and may assign a suitable teacher, room, and weekly schedule. A PLANNING class may have incomplete assignments, while an OPEN or IN_PROGRESS class must have a teacher, a room, and lessons. The system validates the information, assignment conditions, and schedule conflicts before saving. On success, the form closes and the class list is reloaded. 


Related Use Case: UC-CM-02 - Create class.

III. System Design
1. Software Architecture
1.1 Overall Architectural Diagram
  

Figure III.1  Overall architectural diagram
The feature modules execute inside one Spring Boot application. The presentation uses static HTML and JavaScript, with optional separate local serving on port 5500 and backend APIs on port 8080. PayOS is external; application persistence targets Microsoft SQL Server. HTTP is used locally; HTTPS is used for the PayOS API.

Package and Class Naming Conventions
The Java application root is com.talent.management, located under com_be/src/main/java. Feature package names are lowercase with underscores as used in the source, such as course_enrollment and financial_reporting. shared contains config, entity, enums, dto, service and exception.
Classes and interfaces use PascalCase. Methods and fields use lowerCamelCase; constants use UPPER_SNAKE_CASE. Common class suffixes are Controller, Service, ServiceImpl, Repository, Mapper, Request, Response and Dto. ClassEntity names a teaching class without conflicting with java.lang.Class.
com_fe is the editable frontend source: pages contains feature screens; components contains shared HTML; js contains common/page code and admin, finance and tuition-payment folders; css contains common and feature styles. Some screens retain inline JavaScript. scripts/sync-frontend.mjs copies these assets to backend static and legacy webapp locations.
The root Maven project groups com_be. com_be/pom.xml declares Java 17 and Spring Boot 3.3.4. The retained resources/templates files do not establish a configured Thymeleaf application; the starter is not declared.
General StudentController CRUD methods remain placeholders in AuthService; the operational features read existing students through repositories. They are not represented as completed student-management screens.
